# Event

This page defines what counts as an event in the architecture.

## Purpose

Explain the basic unit of occurrence that enters the system and can influence state, expectations, and later reflection.

## Core Idea

An event is a discrete occurrence that can affect the system. It is the basic input unit of the architecture. Events may come from external interaction, internal reflection, pattern recognition, repair, or insight. What matters is not whether the event came from outside or inside, but whether it is meaningful enough to enter the system’s causal history.

The architecture depends on events being discrete and traceable. If a meaningful occurrence cannot be identified as an event, it becomes difficult to explain why a state changed or why a later interpretation exists.

## Event as the Start of Processing

An event is the point at which processing begins. Once an event is recognized, the system can:
- identify the source
- retrieve relevant context
- compare actual outcome against active expectations
- calculate discrepancy
- apply appraisal
- generate emotional impact
- insert resulting effects into history

In this sense, the event is not the whole process. It is the trigger for the process.

## Types of Events

The architecture should allow multiple event types.

### External interaction events
Events that come directly from a counterparty, such as a message, reply, silence, contradiction, compliment, insult, apology, or request.

### Internal reflection events
Events generated by the system while replaying or reconsidering past material.

### Insight events
Events produced when later understanding changes the meaning or significance of a prior event.

### Repair events
Events that signal apology, acknowledgment, changed behavior, consistency, or other conditions that may soften prior damage.

### Pattern events
Events generated when repeated interactions become meaningful as a recurring pattern rather than as isolated moments.

## What Makes Something an Event

Not every tiny detail must become an event. A useful event should be:
- discrete enough to identify
- meaningful enough to affect state or interpretation
- traceable enough to support explanation later

This means event granularity is a design choice. If events are too broad, the system loses detail. If they are too fine-grained, the system becomes noisy and hard to resolve.

## Event Metadata

A useful event may include:
- event identifier
- source
- timestamp
- event type
- basic context
- actual outcome
- links to related prior events, if any

The event itself should record what happened, not the full emotional meaning of what happened. Emotional meaning belongs to later processing layers such as discrepancy, appraisal, and ledger insertion.

## Event vs Interpretation

An event is not the same thing as its interpretation.

For example:
- event: the counterparty did not respond to the joke
- interpretation: the lack of response felt rejecting
- later reinterpretation: the counterparty may have been distracted

The event remains the same even when interpretation changes. This distinction is central to auditability.

## Design Rule

A good event definition should preserve two things at once:
- enough detail to support later explanation
- enough abstraction to keep the model manageable
