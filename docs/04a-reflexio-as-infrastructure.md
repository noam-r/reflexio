# Reflexio as Infrastructure

This page defines the intended scope of Reflexio as a conceptual infrastructure rather than a single application.

## Purpose

Clarify the architectural level of Reflexio and distinguish the core framework from the modules and applications that may be built on top of it.

## Core Idea

Reflexio is not intended to be one specific product, assistant, or workflow. It is a conceptual infrastructure for stateful, expectation-based, explainable affective processing across time.

Its purpose is to define the underlying model:
- how events are represented
- how expectations shape impact
- how discrepancy is interpreted
- how emotional history is recorded
- how current state is derived
- how reflection and reinterpretation work
- how projected futures can be simulated without corrupting history

This infrastructure can then support multiple modules and many different applications.

## What Reflexio Is

Reflexio is:
- a conceptual architecture
- a reusable processing framework
- a set of interoperable state and reasoning layers
- a basis for building reflective, prospective, and hybrid systems
- an infrastructure for auditability and explainability

It defines the rules of the system, not a single user-facing experience.

## What Reflexio Is Not

Reflexio is not:
- one specific journaling app
- one specific decision-support tool
- one specific relationship assistant
- a fixed conversational product
- a single retrospective or prospective workflow

Those may be applications built on top of Reflexio, but they are not Reflexio itself.

## Why This Distinction Matters

Keeping Reflexio at the infrastructure level preserves three important properties.

### 1. Reusability
The same architecture can support multiple modules and multiple applications without being locked to one use case.

### 2. Stability
The conceptual core remains stable even as applications change.

### 3. Clarity
The documentation can distinguish between:
- foundational mechanisms
- reusable capability modules
- application-specific experiences

Without this distinction, the framework risks collapsing into the first compelling product idea built on top of it.

## The Three-Layer View

Reflexio is best understood in three layers.

### 1. Infrastructure layer
The core architecture itself.

This includes:
- state model
- event model
- expectation model
- discrepancy model
- appraisal model
- emotion ledger
- state resolver
- reflection model
- explanation and audit model

### 2. Module layer
Reusable capability modules built on the infrastructure.

Examples:
- retrospective reflection
- prospective reflection
- pattern consolidation
- response policy derivation
- audit query resolution

### 3. Application layer
Concrete tools, products, or interfaces built on one or more modules.

Examples:
- a past-event reflection app
- a conversation planning tool
- a decision-support tool
- a relationship review interface
- a hybrid reflection and simulation assistant

## Design Rule

When writing about Reflexio, the documentation should define the mechanism first, then describe modules, and only then mention example applications.
